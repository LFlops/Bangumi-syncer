## 2. 分模块详细发现

### 2.1 `app/services/summary/service.py`

**H1｜空内容失败判定反向（`service.py:292`）**
```python
if not response.content and not response.model:
```
意图注释是"空内容→失败通知"，但逻辑要求 content **与** model **同时**为空才走失败分支。provider 即便返回空 `choices` 通常也会带上 `model` 名，于是 `not response.model` 为 False → 走到 `_send_success_notification`，**把空总结当作成功发给用户、且吞掉"检查 API key/网络"的失败通知**。应改为 `if not response.content:`。

**M1｜`related_limit` 被 `memory_limit>0` 门控架空（`service.py:210,216-219`）**
```python
memory_enabled = job_config.memory_limit > 0
if memory_enabled:
    memory_context = self._build_memory_context(job_config, task_id, records)
```
`_build_memory_context` 内的 related 分支只在 `memory_enabled` 为真时执行。结果：`memory_limit=0, related_limit>0` 配置下，related 注入与已消费排除全部不发生，`related_limit` 是**死开关**，与独立配置语义及 `memory-stats` 端点（独立累加 related_limit）矛盾。

**M2｜已消费记录被整体剔除出主摘要 prompt（`service.py:211-212` + `229`）**
```python
records = [r for r in records if r.consumed_run_id is None]
...
messages = self._build_messages(records, system_prompt, date_from, date_to)
```
过滤后的 `records` 直接进入 `_build_messages`，即被消费记录**不仅不进"历史上下文"小节，也不进主明细**。当 `lookback_days` 较大、或 job 连跑两次时，LLM 只看到新记录，旧记录"由摘要承继"。这是较 2.0.2"保留明细仅标注"的显著行为变更，closeout E3 用词"不进 prompt"含糊，应**显式文档化**窗口去重语义，否则易被误判为数据丢失。

**L1｜`response.content` 可能为 None 未归一化（`service.py:184,311`）**
失败路径已有 `not ...` 兜底，但成功路径 `summary_text=response.content` 直接透传给 `notification_service.notify`，下游按 str 处理时有 None 序列化/类型风险。建议在出口统一 `content or ""`。

**L2｜`user_name` 三处归一化表达式不一致（`service.py:82,329,370`）**
`job_config.user_name.strip() or None` / `... if ... else ""` / `... or ""` 三种写法，应抽单一 helper 防漂移。

**L3｜多处方法缺类型注解/返回类型（`service.py:283-286,270,321` 等）**
与代码库其余方法的完整注解不一致，尤其 `response` 形参未标注 `ChatResponse`，影响类型检查。

### 2.2 `app/services/summary/models.py` 与 `scheduler.py`

**H2｜`from_config_dict` 裸 `int()` 崩溃整条调度（`models.py:48,51`）**
```python
lookback_days = (int(data.get("lookback_days", 1)),)
max_records = (int(data.get("max_records", -1)),)
```
与同文件受保护的 `_limit`（`try/except`）不同，这两行对非法值（如 `"1.5"`、`"abc"`、手改坏 config）直接抛 `ValueError`。`from_config_dict` 在 `SummaryScheduler._schedule_all_jobs`（`scheduler.py:86`）内无 try 包裹，单个坏配置会**中止整个循环，使所有 summary job 无法（重）注册**；API 的 test/trigger/memory-stats 也会 500。高影响健壮性缺陷。

**M3｜`memory_limit` 钳制 0–1000，与 closeout 第二段 E3 的 1–50 安全意图冲突（`models.py:28,38`）**
代码 `max(0, min(1000, ...))`，`memory_limit` 1000 条 × ~80 字 ≈ 80k+ 字符注入，可能撑爆上下文与 prompt-cache 策略。closeout 第一段 E3 与第二段 E3 对此给出相反结论（见 §3 设计矛盾），须由作者裁决权威边界。

**L4｜魔数 `1000` 多处重复（`models.py:28,38` 与 `extractor.py:54` `prune(keep=1000)`）**
应提取为单一命名常量，防止钳制与 prune 上限漂移。

### 2.3 `app/services/memory/*`

**M4｜`find_overlaps` / `retrieve` 为死代码（`retriever.py:42-69,94-101`、`service.py:96-97`）**
`execute_job` 已改用"硬排除 + 联表反查"，不再调用 `find_overlaps`/`retrieve`（FTS 路径）。其 docstring 仍引用已删除的 `overlap_note` 流程，构成遗留 API 面 + 误导性注释。建议删除或显式标 `@deprecated`，并确认 `agent_memory_fts` 虚表是否在别处仍被依赖。

**M5｜同步 DB I/O 阻塞 async 事件循环（`extractor.py:41,54`；`service.py` 内 `get_recent`/`get_related_titles`）**
`execute_job` 在 Uvicorn 事件循环上运行，但 `store_and_mark`/`prune`/`get_recent`/`get_related_titles` 均为同步阻塞调用，并发调度任务时会串行化/阻塞其它 async 工作。当前体量下影响有限，但属架构性隐患，建议在 executor 中运行或改为异步仓储。

**L5｜`MemoryService.extract_and_store` 的 `messages` 参数缺类型注解（`service.py:43`）**
其余参数均有注解，唯独 `messages` 无，影响可读性与类型检查。

### 2.4 `app/services/llm/providers/openai_compat.py`

**H3｜o 系列模型发 `reasoning_effort` 同时仍无条件发 `temperature`（`openai_compat.py:137-138,143-150`）**
```python
"temperature": kwargs.get("temperature", self.temperature),  # 始终发送
...
if effort is not None:
    body["reasoning_effort"] = effort
```
OpenAI o1/o3/o4-mini 等推理模型**拒绝非 1 的 temperature**（传 `0.7` 直接 400）。Anthropic 侧已正确在 thinking 开启时强制 `temperature=1`（`anthropic.py:165-167`），而 OpenAI 侧未做等价处理 → 双 provider 行为不一致，开启 `thinking_level != off` 且用 o 系列模型时 100% 失败。`_extras_disabled` 降级只去掉 `reasoning_effort`，仍留下非法 `temperature`，无法自救。

**M6｜`max_tokens` 未对推理模型改用 `max_completion_tokens`（`openai_compat.py:137`）**
官方 o 系列要求 `max_completion_tokens`；部分严格网关会拒绝/忽略 `max_tokens`。Anthropic 侧已做模型感知处理，OpenAI 侧没有。

**M7｜OpenAI refusal 被 `ValueError` 后仍被 client 重试（浪费 ~4s）（`openai_compat.py:193-195` + `client.py` 重试）**
拒绝是 HTTP 200 + 解析期 `ValueError`，而 `client.chat` 对所有异常重试，导致确定性错误被重试 2 次（1s+3s 退避）才返回空 `ChatResponse`。refusal 应视为终态错误。`_is_param_rejection` 只匹配 `HTTPStatusError`，无法短路。

**L6｜非 o 模型开启 thinking 时每次调用刷 `logger.warning`（`openai_compat.py:179-182`）**
若全局配置 `thinking_level != off` 但用 `gpt-4o` 类模型，每次 LLM 调用都打 warning，刷屏。应改为 debug 级或只告警一次。

**L7｜`timeout` 参数冗余（`openai_compat.py:118,125`）**
`create_async_client` 与 `client.post` 都传 `timeout=self.timeout`，可能冲突/冗余。

### 2.5 `app/services/llm/providers/anthropic.py` 与 `client.py`

**M8｜`_is_param_rejection` 仅识别 OpenAI 文本且只看 400，Anthropic 与 422 永不降级（`client.py:43-60`）**
- 模式串（`unrecognized` / `unknown parameter` / …）全是 OpenAI 风格；Anthropic 返回 `type: invalid_request_error` + "does not support thinking" 类文案**无一匹配** → Anthropic 参数拒绝不被识别 → 不降级 → 重试后永久失败。
- `resp.status_code != 400` 的硬门槛使基于 FastAPI/pydantic 的 OpenAI 兼容网关（对未知字段如 `reasoning_effort` 返回 **422**）永不触发降级；模式串里的 `"extra fields not permitted"` 因此成为**死代码**（422≠400 永远走不到）。
- 叠加 `anthropic.py:170-176`（任何非 haiku 模型都发 `thinking`/`budget_tokens`），若某非 haiku 模型实际不支持 extended thinking，返回的 400 既无匹配文案又可能被网关转 422 → 该"双保险第二道"降级对 Anthropic 基本失效。

**M9｜重试未区分可重试/不可重试，且忽略 `Retry-After`（`client.py:138-158`）**
401/403（密钥错误）被无效重试 2 次浪费 ~4s；429 被重试但无视 `Retry-After`，退避可能过短（打爆端点）或过长。应按状态码分类：401/403/400 不重试，429/5xx/timeout 重试并尊重 `Retry-After`。

**M10｜provider 契约不一致（影响 Phase3 agent 消费）**
- OpenAI 不映射 `finish_reason → stop_reason`（`openai_compat.py:208` 返回默认 `""`），Anthropic 正常填充（`anthropic.py:236`）。下游据此判断 `max_tokens` 截断时，OpenAI 永远拿不到。
- OpenAI `blocks` 永远 `[]`，Anthropic 返回完整 blocks（text/thinking）。消费推理 token 的能力在双 provider 间不对等，应显式文档化为"已知不一致"或补齐。
- Anthropic 用量漏算 `cache_creation_input_tokens`/`cache_read_input_tokens`（`anthropic.py:220-231`），开启 prompt caching 时 `total_tokens` 偏低，使 `tokens_used`（service.py:249）与 `llm_usage` 的用量归属对 Anthropic 不准确。
- Header：Anthropic 同时发 `Authorization: Bearer` 与 `x-api-key`（`anthropic.py:109-114`），硬编码双 header 味道，对严格网关可能混淆。

**L8｜`latency` 含重试退避墙钟（`client.py:122,129`）**
`latency_ms` 从循环前 `t_start` 算起，成功在第 2 次尝试时报告 ~1s+ 的"延迟"实为退避睡眠，污染 `llm_usage` 延迟统计与可观测性。应只计量成功那次请求。

**L9｜用量日志 `except Exception` 过宽（`client.py:196-197,219-220`）**
fire-and-forget 可接受，但吞掉所有异常（含编程错误）会掩盖 `log_usage` 自身 bug，建议收窄。

**L10｜`anthropic-version` 硬编码（`anthropic.py:113` `"2023-06-01"`）**
应提取为具名模块/类常量，网关要求更新版本时易静默失效。

### 2.6 `app/api/summary_jobs.py` / `app/api/llm.py`

**H1-API｜测试端点空内容误判（`summary_jobs.py:119`）**

`summary_text` 为空但 `usage` 存在时返回 `success=True`（带空文本）。与 `service.py:292` 同源缺陷，预览会"成功"地展示一次失败的（空）LLM 调用。应仅以 `not summary_text` 判定。

```python
injected_count = min(total_count, memory_limit) + related_limit
```

**L11｜重命名流程可能遗留不一致持久态（`summary_jobs.py:70-79`）**
顺序：先 `rename_notification_type`（72）→ `memory_service.rename_task`（74-76）→ `save_summary_config`（77）。若中间步骤抛错，通知类型已落新名而记忆/配置仍旧；且依赖 `save_summary_config(old_name=...)` 真的"删除旧 `[summary-N]` 段"，否则重命名会残留重复配置段。（`config_manager` 重命名语义未读，需核实。）

## 3. 设计层风险与待裁决项

1. **`memory_limit` 权威边界（0–1000 vs 1–50）**：closeout 自我打架，代码/前端/测试均 0–1000。需作者明确：若 1–50 是安全意图，则代码须改为钳制 1–50 并加 `memory_enabled`；若 1000 是意图，则 closeout 第二段 E3/§8/§7 须全面修订为 0–1000。当前若按第二段 E3"修复"代码，会破坏已发布 0–1000 行为及现有测试。
2. **文档单一权威化**：closeout 应合并为单一 E3，删除重复的 1–50 段；子规格 2.0.1/2.0.2 应标注"已被 closeout E2/E3 取代"或删除过期段落；§5 场景3 改用 `--titles`。
3. **消费记录剔除语义**：需在 closeout 明确"整体剔除出主 prompt"而非仅历史小节，避免被误读为数据丢失。
4. **双 provider 契约对齐清单**：`stop_reason`/`blocks`/`cache_* tokens` 的 OpenAI 缺失项应显式列为"已知不一致"或补齐，以免 Phase3 agent 消费时踩坑。

## 4. 修复优先级建议

**P0（先修，HIGH 逻辑/一致性缺陷）**

4. `openai_compat.py` 在发 `reasoning_effort` 时对齐 Anthropic：强制 `temperature=1`（或推理模型改用 `max_completion_tokens` 并移除非法 `temperature`），修复 o 系列 400。

**P1（MEDIUM，正确性/一致性）**
5. 修复 `related_limit` 门控（让其在 `memory_limit=0` 时也能独立生效，或文档明确其为从属开关）。

8. OpenAI 补齐 `finish_reason→stop_reason`，`blocks` 不一致显式文档化；Anthropic 用量补 `cache_*` token。
9. 文档漂移修订（2.0.1/2.0.2/§5 场景3）。

**P2（LOW，规范/健壮性）**
10. `latency` 只计成功请求；`response.content` 出口归一化 `""`；`user_name` 抽 helper；补类型注解。
