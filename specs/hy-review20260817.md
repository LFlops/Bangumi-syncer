## 🔴 高优先级（正确性 / 与 spec 语义冲突）

### 1. `execute_job` 的宽 `try/except` 违背 2.0.2「失败语义表」

**位置**：`app/services/summary/service.py:161-213`

整个执行体（含 `_dispatch_notification`）被包在一个 `try` 里，任何异常都走到 `except` 发
`summary_job_failed` 通知。但 spec 2.0.2 的失败语义表明确要求：

| 失败点 | spec 要求 | 现状 |
|---|---|---|
| chat 失败（LLM 异常） | 不写标记、**不发通知**（重新总结） | 实际发了 `summary_job_failed` 通知 ❌ |
| 通知失败（投递层） | 标记已写、失败、**不二次通知** | 实际又走到外层 `except` 发**第二条**不同通知 ❌ |

且 `summary_llm_failed`（响应为空时 `_dispatch_notification` 发的）与 `summary_job_failed`
（外层发的）是两类不同通知，语义重叠。

**建议**：按 spec 拆成窄捕获，使各失败点语义与文档一致：

```python
try:
    response = await self.llm_client.chat(messages, job_name=job_config.name)
except Exception as e:
    logger.error(f"LLM chat failed for '{job_config.name}': {e}")
    return  # 与 spec 对齐：chat 失败不标记、不通知（产品若希望告知，改发 summary_llm_failed 而非通用 job_failed）
if job_config.memory_enabled:
    run_id = str(uuid4())
    try:
        await self.memory.extract_and_store(...)
    except Exception as e:
        logger.error(f"Failed to store memory: {e}")
try:
    self._dispatch_notification(job_config, response, records, date_from, date_to)  # 置于最外层之外
except Exception as e:
    logger.error(f"Notification failed for '{job_config.name}': {e}")  # 不二次通知：标记已写，投递失败由通知重试/告警兜底
```

### 2. 删除 summary job 不清理记忆 → 孤儿数据 + 悬挂消费标记

**位置**：`app/api/summary_jobs.py:84`（`delete_summary_job`）

`delete_summary_job` 只调 `delete_summary_config / reload_config / apply_config_after_save`，
**没有**调 `memory_service.clear_task(...)`。后果：

- `agent_working_memory` + `_archive` 里该 `task_id` 的记忆行变成不可达死数据
  （`retrieve` 必须按 task_id 查，task 已删则永远查不到）；
- `sync_records.consumed_run_id` 仍指向已不存在的 run_id。下次用**同名**重建 job 时，
  今日明细会被旧 run_id 误判为“已消费”，产生虚假 overlap 提示。

**建议**：`delete_summary_job` 内补一行
`memory_service.clear_task("summary", f"summary-{decoded}")`
（同一事务清主表 + 归档 + 消费标记，spec C3/C12 已具备能力；删除属不可恢复操作，无需二次确认）。

## 🟡 中优先级（召回 / 功能偏差）

### 3. 检索关键词漏了 `user_filter`（spec 明确要并集）

**位置**：`specs/agent-phase2.0.2-read-memory.md` 的 `execute_job` 片段 vs `app/services/summary/service.py:101-115`

spec 2.0.2 写明 `keywords = [job_config.user_filter or ""] + [r.bgm_title ...][:5]`，
但实现 `_build_memory_context` 只取 `bgm_title`，且 `SummaryJobConfig` 根本没有 `user_filter` 字段。
即 spec 规定的“用户过滤词也作为检索词”这一源被丢掉了。`user_filter` 是用户显式关心的
番剧/用户维度，应当纳入 FTS 召回。

**建议**：补回该源（若产品上 `user_filter` 在 summary 场景已弃用，应同步改 spec 说明，避免文档与代码持续分叉）。

### 4. `search_fts` 按空白切词，破坏多词标题短语

**位置**：`app/core/database/agent_memory.py:220-225`

```python
terms = ['"' + t.replace('"', '""') + '"' for t in query.split() if len(t.strip()) >= 3]
```

`query` 是 `_build_memory_context` 把所有标题用空格 join 后传入，这里再 `query.split()` 会
**把带空格的标题切碎**。例如 `"Spy x Family"` → `"Spy" OR "Family"`，丢失短语整体匹配；
中文标题虽无空格通常 OK，但英文/含空格标题召回失真。

**建议**：每个标题作为一个 phrase 直接 OR 拼接，不在内部二次切分：

```python
phrases = ['"' + k.replace('"', '""') + '"' for k in keywords if len(k.strip()) >= 3]
match = " OR ".join(phrases)
```

调用侧把 `keywords` 列表直接传入 `search_fts`，内部不再对 `query` 做 `split()`。

### 5. `full_text` 未进 FTS，关键词召回只靠 `summary` 短句

FTS5 表只建在 `(task_type, summary, outcome)`，`full_text`（总结全文）**不索引**。
`search_fts` 只能命中 LLM 生成的一行 `summary`。若摘要漏写某番剧名，则该历史记忆永远无法被
该标题召回。spec 虽把 `full_text` 定位为“回溯/诊断用”，但既然 `search_fts` 是中期记忆主检索手段，
建议评估把 `full_text` 也加进 external-content FTS（触发器同步加列即可），显著改善召回。

### 6. `retrieve` 关键词命中无总上限

spec 明确“keywords 命中不占 `memory_limit` 额度”，当前 `retrieve` 对 FTS 命中**完全不收束**
（仅各自 `limit`）。记忆量小时无碍，但某标题高频命中数十上百条时会撑爆注入 token。

**建议**：加软上限（如 `limit * 3` 或固定 20），防止异常膨胀。

## 🟢 低优先级（整洁性 / 健壮性）

### 7. `MemoryService(sync_records_repo=...)` 参数从未使用

`app/services/memory/service.py` 存了 `self._sync = sync_records_repo` 却从不引用——
`store_and_mark` / `clear_task` 是经**共享 connection** 直接操作 `sync_records` 表
（spec D5/D7 的折中）。该形参纯属误导（spec 实例化示例只是示意）。

**建议**：删掉该形参；或改为在 store/clear 里显式用 `sync_records_repo` 替代“穿透式”访问，
让依赖关系清晰、可测试。

### 8. `consumed_run_id` 无索引

`clear_task` 的 `UPDATE sync_records SET consumed_run_id = NULL WHERE consumed_run_id IN (...)`
在 `consumed_run_id` 上无索引，会全表扫。clear 低频影响小，但若 `sync_records` 量大可加一个
轻量索引；`find_overlaps` 走 Python 已加载集合无需索引。

### 9. `overlap_note` 在 `context` 为空时多出前导空行

`app/services/summary/service.py:120`：`context = f"{context}\n{_OVERLAP_NOTE}{lines}"`
当没有历史摘要却有 overlap（边界情形）时，拼进 system prompt 会多一个空行。

**建议**：用条件拼接或 `textwrap.indent` 统一格式，保持注入文本干净。

## 演进建议（对齐 spec 自家“改进方向”）

- **显式记忆类别字段**：spec 总览自承“三层无显式记忆类别标记，靠 `task_type`/`outcome`/独立表隐含”。
  Phase 2.3 要“feedback 优先”时，集中改 `_deduplicate_and_rank` 即可，但加一个 `category`
  （short/mid/long）或复用 `outcome` 会更利于后续加权与 Phase 3 诊断统一检索。
- **反馈条目长期策略**：当前 `prune` 跳过 `outcome='feedback'`，但 `clear_task` 会一并删。
  spec 已给“复制新 job 保留偏好”的出路，建议前端明确提示这点，避免用户误清空。

## 小结

- 最高价值两项（**#1 失败语义与 spec 冲突**、**#2 删 job 泄漏记忆**）属“行为正确性”层面，建议优先修；
- #3–#5 为召回质量偏差；#6–#9 为整洁性/健壮性。
- 全量测试现状：3237 passed / 5 xfailed（与开发终态一致），以上改动均应为增量修补、不破坏既有行为。
