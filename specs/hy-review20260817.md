## 🔴 高优先级（正确性 / 语义冲突）

### 1. `execute_job` 错误处理分散、行为不一致 —— ✅ 已修复（2026-08-20）

**原问题（检视时）**：`app/services/summary/service.py` 的 `execute_job` 把整个执行体
（含 `_dispatch_notification`）包在一个宽 `try` 里；后续修成三个狭窄 try/except 后，
又出现行为不一致：chat 失败静默 return 不发通知、store 失败吞掉继续发成功通知、
notify 失败记日志——与 spec 2.0.2「失败语义表」互相矛盾（chat 失败不通知；通知失败不二次通知）。

**产品决策（2026-08-20 定稿）**：**总结过程任何阶段出错都要通知用户**，不做静默吞掉；
只是按失败阶段（`query` / `chat` / `store`）区分通知类型与文案，方便用户定位问题环节。
**唯一例外**：通知投递本身失败（`stage=notify`）时不二次通知——投递层问题走通知重试/告警兜底，
重发可能重复失败。

**最终实现**（`app/services/summary/service.py`）：

- 模块级阶段常量 `_STAGE_QUERY` / `_STAGE_CHAT` / `_STAGE_STORE` / `_STAGE_NOTIFY`，
  及 `_STAGE_FAILURE_META`（每阶段的 `inbox_type` / `inbox_title` / `inbox_body` / `summary_prefix`）；
- `execute_job` **改回单一 `try/except`**，用局部变量 `stage` 随流程推进标记当前阶段；
  任何异常统一进入同一 `except`（`stage=notify` 时仅记日志并 return）；
- 新增 `_send_stage_failure_notification(job_config, stage, error)`：按 `_STAGE_FAILURE_META[stage]`
  组装短信/标题/正文/类型，复用现有 `_send_failure_notification`。

最终行为：

| 阶段 | 通知类型 | 文案定位 |
|---|---|---|
| query 失败 | `summary_job_failed` | 「执行异常（查询/构建阶段）· 请检查任务配置」+ 具体错误 |
| chat 失败 | `summary_llm_failed` | 「LLM 调用失败（LLM 调用阶段）· 请检查 API 地址和密钥」+ 具体错误 |
| store 失败 | `summary_job_failed` | 「任务异常（记忆写入阶段）· 记忆写入失败，下次将重新总结」+ 具体错误 |
| notify 失败 | 不二次通知（唯一例外） | 仅日志，投递层重试/告警兜底 |

**测试**：`test_chat_exception_sends_llm_failed_notification`（chat 异常也要通知、
类型 `summary_llm_failed`、日志含 `stage=chat`）；新增 `test_store_failure_sends_failed_notification`
（store 失败通知 `summary_job_failed`、文案含「记忆写入阶段」、日志含 `stage=store`）；
`test_exception_in_query_is_caught` / `test_notification_failure_no_second_notification` 断言保持成立。

> ⚠️ **行为变更**：`store` 失败由 spec 2.0.2 原「照发成功通知」改为「发失败通知」
> （按产品决策：总结过程出错就通知）。若日后想恢复「store 失败不打扰用户」，
> 只需把 `_STAGE_FAILURE_META[store]` 改为仅记日志即可（策略集中点）。

### 2. 删除 summary job 不清理记忆 → 孤儿数据 + 悬挂消费标记 —— ✅ 已修复（2026-08-20）

**位置**：`app/api/summary_jobs.py:84`（`delete_summary_job`）

原实现只调 `delete_summary_config / reload_config / apply_config_after_save`，**没有**调
`memory_service.clear_task(...)`。后果：

- `agent_working_memory` + `_archive` 里该 `task_id` 的记忆行变成不可达死数据
  （`retrieve` 必须按 task_id 查，task 已删则永远查不到）；
- `sync_records.consumed_run_id` 仍指向已不存在的 run_id。下次用**同名**重建 job 时，
  今日明细会被旧 run_id 误判为“已消费”，产生虚假 overlap 提示。

**已修复**：`delete_summary_job` 删除配置后补调
`memory_service.clear_task("summary", f"summary-{decoded}")`
（同一事务清主表 + 归档 + 消费标记，spec C3/C12 能力现成）。

**测试**：`test_deletes_job_and_calls_scheduler` 补 `clear_task` 断言
（`("summary", "summary-Dad Summary")`）。

## 🟡 中优先级（召回 / 功能偏差）

### 3. 检索关键词漏了 `user_filter` —— ✅ 已修复（2026-08-20：spec 同步，删除 user_filter 引用）

**位置**：`specs/agent-phase2.0.2-read-memory.md` 的 `execute_job` 片段 vs `app/services/summary/service.py:101-115`

复核后更正：`user_filter` 是 **feiniu 专属字段**（`app/core/config.py:558` 在 `get_feiniu_config` 内），
而 summary 配置段 `_SUMMARY_FIELDS`（`config.py:679`）与 `SummaryJobConfig` 都没有该字段。
即 spec 2.0.2 的 `keywords = [job_config.user_filter or ""]` **引用了一个 summary 域不存在的字段**——
实现方正确地放弃了它，只保留 `bgm_title` 源。

**已做（2026-08-20，改 spec 不改代码）**：已删除 2.0.2「关键设计点 / execute_job 片段 / Scenario R5」三处与
总览「关键词来源」两处的 `user_filter` 表述，注明 summary 关键词仅取今日明细 `bgm_title`（去重前 5）。

### 4. `search_fts` 按空白切词，破坏多词标题短语 —— ✅ 已修复（2026-08-20）

**位置**：`app/core/database/agent_memory.py`（原 `search_fts` 用 `query.split()` 按空白切词）

原实现把 `_build_memory_context` 空格 join 的标题字符串再 `split()`，会把带空格的标题切碎
（`"Spy x Family"` → `"Spy" OR "Family"`），丢失短语整体匹配、召回失真。

**已修复**：`search_fts` 签名由 `query: str` 改为 `terms: list[str]`——**每个关键词作为一个整体
phrase** 做 `OR` 拼接，不在内部二次切分；`retriever.retrieve` 直接把过滤后的 `clean` 列表传给 repo，
去掉 `" ".join(clean)`。

**测试**：repo 层 `test_search_fts_multi_word_title_phrase_match`（`"Spy x Family"` 只命中含
完整短语的记忆，不命中 `Family Guy`）；retriever 层 `test_multi_word_keyword_passed_as_single_phrase`。

### 5. `full_text` 未进 FTS，关键词召回只靠 `summary` 短句 —— ⬜ 待办（Phase 3 可选增强）

FTS5 表只建在 `(task_type, summary, outcome)`，`full_text`（总结全文）**不索引**。
`search_fts` 只能命中 LLM 生成的一行 `summary`。若摘要漏写某番剧名，则该历史记忆永远无法被
该标题召回。spec 已把 `full_text` 定位为“回溯/诊断用”，属有意的设计取舍。

**建议**：若需要改善中期记忆召回，把 `full_text` 加进 external-content FTS。
注意 FTS5 virtual table 无法 `ALTER ADD COLUMN`，需版本化迁移（DROP 触发器 → DROP FTS 表 →
重建含 `full_text` 列 → 从主表回填 → 重建触发器）。投入中等，建议 Phase 3 诊断真正需要全文召回时再做。

### 6. `retrieve` 关键词命中无总上限 —— ⬜ 待办（Phase 3 低风险健壮性）

spec 明确“keywords 命中不占 `memory_limit` 额度”，当前 `retrieve` 对 FTS 命中**完全不收束**
（仅各自 `limit`）。记忆量小时无碍，但某标题高频命中数十上百条时会撑爆注入 token。

**建议**：加软上限（如 `limit * 3` 或固定 20），防止异常膨胀。

## 🟢 低优先级（整洁性 / 健壮性）

### 7. `MemoryService(sync_records_repo=...)` 参数从未使用 —— ✅ 已修复（2026-08-20）

`app/services/memory/service.py` 存了 `self._sync = sync_records_repo` 却从不引用——
`store_and_mark` / `clear_task` 是经**共享 connection** 直接操作 `sync_records` 表
（spec D5/D7 的折中）。该形参纯属误导（spec 实例化示例只是示意）。

**已做（2026-08-20）**：删除该形参——`MemoryService(memory_repo)` 单参构造，调用方
（summary service / API / 测试）同步移除实参；消费标记继续经共享 connection 穿透式访问。

**测试**：构造调用点全部改单参（`tests/services/memory/test_service.py`、`tests/services/summary/test_service.py`）。

### 8. `consumed_run_id` 无索引 —— ✅ 已修复（2026-08-20）

`clear_task` 的 `UPDATE sync_records SET consumed_run_id = NULL WHERE consumed_run_id IN (...)`
在 `consumed_run_id` 上无索引，会全表扫。clear 低频影响小，但若 `sync_records` 量大可加一个
轻量索引；`find_overlaps` 走 Python 已加载集合无需索引。

**已做（2026-08-20）**：`connection.py` 索引区新增 `idx_sync_records_consumed_run_id`
（CREATE INDEX IF NOT EXISTS 幂等，老库补列后同样生效）。

**测试**：`test_sync_records_consumed_run_id_index_created`（sqlite_master 断言索引存在）。

### 9. `overlap_note` 在 `context` 为空时多出前导空行 —— ✅ 已修复（2026-08-20）

`app/services/summary/service.py` 的 `_build_memory_context`：
`context = f"{context}\n{_OVERLAP_NOTE}{lines}"`，当没有历史摘要却有 overlap（边界情形）时，
拼进 system prompt 会多一个空行。

**已做（2026-08-20）**：改条件拼接——`context` 为空时直接以标注开头
（`context = f"{context}\n{note}" if context else note`），非空时保持原格式不变。

**测试**：`test_overlap_note_with_empty_context_no_leading_blank_line`（断言「## 历史执行上下文」后无前导空行）。

## 演进建议（对齐 spec 自家“改进方向”）

- **显式记忆类别字段**：spec 总览自承“三层无显式记忆类别标记，靠 `task_type`/`outcome`/独立表隐含”。
  Phase 2.3 要“feedback 优先”时，集中改 `_deduplicate_and_rank` 即可，但加一个 `category`
  （short/mid/long）或复用 `outcome` 会更利于后续加权与 Phase 3 诊断统一检索。
- **反馈条目长期策略**：当前 `prune` 跳过 `outcome='feedback'`，但 `clear_task` 会一并删。
  spec 已给“复制新 job 保留偏好”的出路，建议前端明确提示这点，避免用户误清空。
